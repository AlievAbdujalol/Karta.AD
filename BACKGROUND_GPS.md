# Ограничения фоновой геолокации (PWA Karta-AD)

Статус: **актуальные ограничения платформы**, зафиксированные при реализации
системы отслеживания транспорта (п. 6 ТЗ). Это не список пожеланий, а
документированные границы, в рамках которых работает текущая реализация.

## Тип приложения

Karta-AD — **веб-приложение / PWA** (React + service worker + web manifest),
а не нативное Android/iOS-приложение. Весь GPS-код — обычный
`navigator.geolocation.watchPosition` внутри вкладки браузера.

## Что подтверждено кодом

| Возможность | Реализация | Граница |
| --- | --- | --- |
| GPS при открытой вкладке | `TripContext.startGpsWatch` (`watchPosition`, `enableHighAccuracy`), `NavigationContext.startGps` | работает, пока вкладка активна |
| Heartbeat координат | `TripContext`: запись `last_updated` каждые 30 с | работает при живой вкладке; свежесть ≥3 мин — иначе транспорт помечается неактивным (`isVehicleLive`) |
| Service worker / Push | `public/sw.js`, `src/lib/push.js` | push-уведомления могут приходить и в фоне **только если SW не выгружен ОС** |
| Восстановление рейса после перезагрузки | `TripContext`: чтение активного `vehicles`-ряда + `karta_trip_started_at` | работает, если вкладка не выгружена памятью устройства |

## Чего PWA **не может** гарантировать (ограничения платформы)

1. **Заблокированный экран (Android/iOS).** ОС приостанавливает
   JavaScript вкладки. `watchPosition` перестаёт получать фиксы — координаты
   «замерзают» на последнем значении. Мы это честно показываем:
   `gpsFreshness` → `stale` через 180 с, статус «Данные устарели»,
   ETA → «Время прибытия неизвестно», транспорт исчезает из списка активных.
2. **Переключение в другое приложение.** Анаично: таймеры и GPS-回调
   приостанавливаются. Восстановление — при возврате во вкладку (первый
   фикс `watchPosition` обычно приходит за 1–5 с).
3. **Непрерывный фоновый GPS средствами веб-страницы невозможен.**
   Нет аналога Android foreground service / iOS significant-location-change
   у обычной вкладки. Требование «продолжать отслеживание при заблокированном
   экране» **штатными средствами PWA не выполняется** — это ограничение
   зафиксировано, а не обойдено.
4. **Фоновый push не равен фоновому GPS.** SW может показать уведомление,
   но новые координаты транспорта в фоне не придут, если вкладка выгружена;
   пассажир увидит их после возврата в приложение (или из опроса, если ОС
   оставила вкладку в памяти).
5. **iOS Safari** дополнительно ограничивает `watchPosition` в фоне
   (примерно 30–60 с работы после ухода в фон, затем — до ~5 раз в час
   на фоновые обновления геолокации у веб-приложений).

## Пассажир vs водитель (по ТЗ)

- **Пассажиру** непрерывный фоновый GPS не нужен: расстояние и ETA
  считаются локально из координат транспорта (сервер не получает позицию
  пассажира). При блокировке экрана сохраняются выбранный маршрут и
  остановка (`watchedStop`), уведомления — при живой вкладке/SW.
- **Водителю** при активном рейсе GPS продолжает работать, пока вкладка
  активна. Для реальной фоновой передачи координат во время рейса
  **необходима нативная реализация** (см. ниже).

## Что предложено вместо веб-фона (нативная реализация)

Для надёжного отслеживания при заблокированном экране требуется одно из:

1. **Android-приложение (или Capacitor/TWA-обёртка)** с:
   - разрешением `ACCESS_FINE_LOCATION` (+ `ACCESS_BACKGROUND_LOCATION`
     только по явной необходимости и с объяснением водителю);
   - foreground service с постоянным уведомлением «Рейс идёт» во время
     активного рейса и его остановкой по `endTrip` (скрытого слежения
     после завершения рейса быть не должно);
   - восстановлением после убийства процесса и потерии GPS.
2. **Серверный трекинг устройства** (трекер/тахограф) — если координаты
   идут с устройства, а не из браузера.

Ни один из вариантов в рамках этого ТЗ не реализуется: проект остаётся
PWA, ограничение зафиксировано документом и проверяется чек-листом ниже.

## Ручной чек-лист проверки на реальных устройствах

Автоматизировать эти сценарии в CI нельзя (нужны физическое устройство и
экран). Проверяются вручную перед релизом функциональности:

1. **Сценарий 8 — экран заблокирован:**
   - открыть карту пассажира, выбрать остановку, погасить экран на 5 мин;
   - после разблокировки: статус транспорта «Данные устарели», ETA
     «неизвестно», никаких ложных «прибыл» за время блокировки.
2. **Сценарий 9 — водитель переключился в другое приложение:**
   - активный рейс, переключение на мессенджер на 2–3 мин;
   - после возврата: координаты обновились, `last_updated` свежий,
     машина состояний остановки не «перепрыгнула» этапы.
3. **Фоновый push:** заблокировать экран с разрешёнными уведомлениями —
   уведомление о прибытии приходит только если ОС не выгрузила SW
   (проверить на Android Chrome и iOS Safari отдельно — поведение разное).
4. **Отказ в геолокации (сценарий 13):** запретить доступ — приложение
   не падает, позиция «я на карте» не рисуется, ETA до пользователя
   скрыто (без выдуманных расстояний).
5. **Потеря сети (сценарии 10–11):** режим «в самолёте» на 2 мин —
   индикатор офлайна, после возврата сети — немедленный рефетч и
   восстановление статусов.

## Вывод для владельца проекта

- Требование п.6 ТЗ «отслеживание продолжается при заблокированном
  экране» **выполнено в пределах возможностей PWA**: честные статусы
  устаревания, антидубли, отсутствие ложных событий — но **не** непрерывным
  GPS в фоне. Непрерывное фоновое отслеживание требует нативного приложения
  (Android foreground service) — это отдельная задача и отдельная оценка.
