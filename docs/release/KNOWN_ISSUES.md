# Известные ограничения и открытые вопросы

- **Дата:** 02.11.2026
- **Ветка:** `main` (baseline `6aeeccb` + незакоммиченные правки релизного аудита)
- **Связанные документы:** `BASELINE_AUDIT.md`, `TEST_RESULTS.md`, `RELEASE_CHECKLIST.md`

В этом файле — только то, что **не исправлено** и требует решения продукта,
доступа или ручной проверки. Исправленные дефекты (RA-01…RA-05) описаны в
`BASELINE_AUDIT.md` и здесь не дублируются.

## 1. Продуктовые решения (блокируют включение реальных оплат)

### KI-01 · Тестовый платёж помечает заказ оплаченным (RA-06, P2)

- **Где:** `src/lib/paymentProviders.js:42` → RPC `public.create_store_payment`
  (`SECURITY DEFINER`, `EXECUTE` у `anon` и `authenticated`).
- **Что происходит:** при `p_provider = 'mock'` платёж сразу получает статус
  `succeeded`. Сумма берётся из `orders.total` на сервере (подделать сумму
  нельзя), но **инициатор платежа не проверяется** — достаточно знать `order_id`.
- **Почему это ещё не инцидент:** реальные провайдеры (`alif`, `eskhata`,
  `dushanbe_city`) в реестре помечены `available: false`; клиент вызывает
  только `mock`, и это демонстрационный сценарий. RLS на `payments` не даёт
  читать чужие платежи.
- **Риск при запуске реальных оплат:** заказ можно пометить оплаченным без денег.
- **Варианты решения (выбрать один до подключения провайдера):**
  1. Выключить `mock` в проде флагом (env/настройка бизнеса) — минимальное изменение.
  2. Разрешить `mock` только `service_role`, а создание платежа перенести в
     серверный webhook провайдера.
  3. Оставить `mock` только для `authenticated` + проверять, что `orders.user_id`
     (или телефон) совпадает с вызывающим.
- **Кто решает:** продукт + владелец платёжной интеграции.

## 2. Принятые риски (осознанно не меняем сейчас)

### KI-02 · Трекинг заказа магазина по UUID (RA-07, P3)

- `get_store_order_tracking(p_order_id)` доступна `anon`, окно — 30 дней.
- Возвращает: статус, состав заказа, суммы, адрес и координаты доставки.
  **Не возвращает** имя и телефон клиента.
- UUID — bearer-токен: перебор невозможен, но ссылка сама является секретом
  (попадёт в историю браузера/логи — заказ станет читаемым).
- **Решение:** приемлемо для гостевого трекинга. Если потребуется строгая
  приватность — одноразовый подписанный токен, как в `delivery-api`.
- **Триггер пересмотра:** если в трекинг добавят имя/телефон/точную квартиру.

### KI-03 · Кэш позиции в `MapControls` без проверки точности (RA-08, P3)

- `src/components/MapControls.jsx:59` — кэш до 5 минут показывается как
  «Вы на карте» без проверки `accuracy`.
- В `src/pages/Home.jsx:426` та же логика уже требует `accuracy ≤ 100 м`;
  здесь проверки нет.
- **Почему не исправлено сейчас:** ветка используется только когда снаружи не
  передан `onLocate` (Home передаёт свой обработчик, у него проверка есть);
  изменение поведения кнопки требует проверки на реальном устройстве с плохим
  GPS, которого в этой среде нет.
- **Кандидат в P3-бэклог.** Правка на 3 строки: кэш применять только при
  `Number.isFinite(accuracy) && accuracy <= 100`, иначе — свежий запрос.

### KI-04 · `spatial_ref_sys` без RLS (RA-09, P3)

- Единственная таблица `public` без RLS — системная таблица PostGIS
  (`rls_disabled_in_public` в advisor).
- Пользовательских данных не содержит; включение RLS может сломать расширение
  и запросы геометрии.
- **Решение:** оставляем как есть, фиксируем здесь.

## 3. Инфраструктура и доступы (вне кода)

### KI-05 · `ai-proxy` вернёт 503 без секрета

- `supabase/functions/ai-proxy` требует `OPENROUTER_API_KEY` в secrets проекта.
- Сейчас секрет не задан → функция отвечает 503, AI-конструктор уходит в
  прямой режим (если задан `VITE_OPENROUTER_API_KEY`) или показывает ошибку.
- **Действие:** Supabase Dashboard → Project Settings → Edge Functions → Secrets.
  CLI не использовать: токен в этой среде недействителен
  (`LegacyInvalidAccessTokenError`).

### KI-06 · Ротация ключей, попавших в историю git

- В `.env.example` прямо указано: если `VITE_CARTO_API_KEY`,
  `VITE_GOOGLE_MAPS_KEY` или `VITE_GEMINI_API_KEY` попадали в историю — считать
  скомпрометированными и выпустить новые.
- Проверить историю и ротировать может только владелец аккаунтов (Google Cloud,
  CARTO, Google AI Studio). Автоматической проверки в CI нет.
- **Действие:** владелец проекта — проверить `git log -p -- .env*`, ротировать
  при необходимости, ограничить ключи доменами.

### KI-07 · `auth_leaked_password_protection` выключен

- Advisor Supabase рекомендует включить проверку паролей по утечкам
  (HaveIBeenPwned). Включается только в Dashboard: Authentication → Providers →
  Email → Leaked password protection.
- **Действие:** владелец проекта, до публикации.

### KI-08 · Vercel MCP недоступен (403, team scope)

- Проверить состояние деплоя, домены и переменные окружения через MCP нельзя.
- **Действие:** проверять в Dashboard Vercel вручную по чек-листу
  `RELEASE_CHECKLIST.md` §4.

### KI-09 · Supabase CLI не работает в этой среде

- `supabase` CLI возвращает `LegacyInvalidAccessTokenError`; `supabase db push`
  и `supabase secrets set` недоступны.
- **Следствие:** DDL применяется только через Dashboard SQL Editor или MCP
  `apply_migration`; секреты — только через Dashboard.
- **Риск:** расхождение «миграция в репозитории ≠ применена в БД». Контроль —
  таблица применённых миграций в `RELEASE_CHECKLIST.md` §2.

## 4. Что нельзя было проверить в этой среде

Это не дефекты, а **границы доказательной базы**. Перед публикацией их нужно
закрыть ручной проверкой.

| # | Не проверено | Почему | Как проверить |
|---|---|---|---|
| 1 | UI-клики под живым аккаунтом | Вход только через Google OAuth, автоматизированного доступа нет | Ручной проход по `RELEASE_CHECKLIST.md` §5 под тестовым аккаунтом |
| 2 | Реальный GPS: туннель, фон, «прыжок» | Нет устройства с GPS | Пройти маршрут с приложением в фоне; проверить, что после туннеля позиция догоняется |
| 3 | Экран 360 px, safe-area, «чёлка» | Нет устройств/эмулятора в этой среде | DevTools → 360×640 + реальный iPhone/Android |
| 4 | Push-уведомления | Нужны VAPID-ключи и разрешение браузера | Включить push, проверить доставку (см. `push_*` таблицы) |
| 5 | Реальная оплата | Провайдеры `available: false` | После решения KI-01 |
| 6 | Деплой и прод-URL | Vercel MCP 403; деплой не запускался | После разрешения на push — проверить `deploy.yml` и прод-URL |
